# 채팅 브로커 전략

## 핵심 문제

채팅 브로커는 메시지를 구독 중인 클라이언트에게 전달하는 역할을 한다.  
브로커 선택은 서버 운영 방식(단일 vs 다중 인스턴스)에 따라 결정된다.

```
클라이언트 A → SEND → [서버] → [브로커] → PUSH → 클라이언트 B, C, D
```

---

## 비교

### SimpleBroker

Spring이 JVM 메모리 내에서 구독자 목록을 관리하는 인메모리 브로커.

**장점**
- 별도 인프라 불필요, 설정 최소
- 단일 서버에서 지연 시간 최소

**한계**
- 서버가 2대 이상이면 인스턴스 간 구독자 목록이 분리되어 메시지 전달 불가
- 서버 재시작 시 구독 정보 소멸

---

### Redis Pub-Sub

Redis를 중앙 메시지 버스로 사용.  
각 서버 인스턴스가 Redis 채널을 구독하다가 메시지가 발행되면 자신에게 연결된 클라이언트에게 전달한다.

**장점**
- 수평 확장 가능
- 프로젝트에 이미 Redis 도입됨 — 인프라 추가 없음
- SimpleBroker → Redis 전환 시 Service 계층 코드 변경 없음

**한계**
- Fire-and-Forget 방식 — 수신자 없거나 서버 다운 시 메시지 유실  
  (히스토리는 DB에 저장하므로 실용적 영향은 제한적)
- 메시지 순서 미보장

---

### Kafka

분산 로그 기반 메시지 스트리밍 플랫폼. 메시지를 토픽에 저장하고 컨슈머 그룹이 순서대로 읽는다.

**장점**
- 메시지 내구성, 순서 보장, 재처리 가능
- 초당 수백만 건 처리 가능

**한계**
- 채팅 실시간 전달에 수 ms ~ 수십 ms 추가 지연
- Zookeeper/KRaft + 브로커 운영 필요 — 현 규모 대비 오버엔지니어링
- WebSocket 실시간 전달에 별도 처리 필요

---

### RabbitMQ / ActiveMQ

Spring WebSocket의 STOMP 릴레이 기능으로 외부 STOMP 브로커를 연결하는 방식.

**장점**
- Spring WebSocket 공식 통합
- 메시지 내구성 (RabbitMQ 기준)

**한계**
- Redis와 역할이 겹치지 않아 별도 인프라가 됨
- 이미 Redis가 있는 이 프로젝트에서는 불필요한 스택 추가

---

## 채택 전략

| 단계 | 브로커 | 이유 |
|---|---|---|
| **현재 (단일 서버)** | SimpleBroker | 인프라 추가 없이 즉시 구현, 단일 서버에서 충분 |
| **서버 스케일아웃 시** | Redis Pub-Sub | 이미 Redis 도입됨, 코드 변경 최소, 채팅 규모에 적합 |
| **마이크로서비스 분리 + 대용량** | Kafka | 채팅 서비스 독립 운영, 메시지 내구성·순서 보장이 필요한 시점 |
